# RTMP 转 WebRTC 低延迟直播方案：测试文档

> 文档范围：`ngx-rtc-module` 的测试方法与判定标准——测试分层、推流环境、端到端（werift）、鉴权、HTTP-FLV 兜底与局域网 candidate 验证。所有命令在本仓库 `/home/dgliu/workspace/webrtc/` 下执行。

**结论**：权威验收口径是「werift 无头播放器端到端收包」：`./run.sh verify` 判定 `audio.pkts>0 && video.pkts>0` 即 PASS，实测值视频 H264 761 包/362 KB、音频 Opus 389 包/67 KB、首包约 560 ms，`play.mjs` 另打印 `video: first_keyframe_ms`（首个 H264 IDR 到达，真正出图延迟口径）。在此基础上叠加三层轻量验证：信令鉴权（有效 HMAC token→`code=0`，错误/缺失/过期 token→403，限流→429）、HTTP-FLV 兜底（带有效 token→HTTP 200 + `FLV` 文件头，无 token→403）、局域网 candidate（answer 含 `a=candidate ... <探测 IP> 8000 ...`）。纯 C 协议核心 host 单测：`ngx-rtc-module/test/` 145 用例全 PASS（Linux 上对真实 nginx 头文件编译），并曾以回归断言拦截 B 帧识别缺陷（Exp-Golomb 后缀按位或累加导致 slice_type 6/2 误判），修复后转绿；另有 `scripts/sanitize-tests.sh`（ASan/UBSan/TSan）与 `scripts/cross-win64-tests.sh`（交叉出 `run_tests.exe`）两个驱动。

## 1 结论与测试分层

| 层 | 对象 | 手段 | 结果 |
| --- | --- | --- | --- |
| L0 纯 C 单测 | rtp/sdp/stun/rtcp/hsm/session_fsm/core/ring/avsync/jitter/shm/stream_module | host 单测（Linux 对真实 nginx 头文件编译，无 nginx 运行时依赖） | `ngx-rtc-module/test/` 145 用例全 PASS |
| L1 端到端收包 | 全链路 | `run.sh` + `play.mjs`（werift） | `run.sh verify` 收包判定 |
| L2 信令与鉴权 | `/rtc/v1/play/` + Lua | curl 注入 key 变体 | 通过（403/429 分支覆盖） |
| L3 兜底与网络 | HTTP-FLV、candidate | curl + `ss` + 抓包 | 通过 |

结果基线（作为预期输出参考）：

| 指标 | 实测值 |
| --- | --- |
| 信令响应 | `{"code":0,...}` |
| 视频 | H264 761 包 / 约 362 KB |
| 音频 | Opus 389 包 / 约 67 KB |
| 首包时延 | 约 560 ms（`first_packet_ms`） |
| 视频首帧 IDR | `first_keyframe_ms`（首个 H264 IDR 到达，出图口径） |
| candidate | 自动探测主网卡 IP + `:8000`（本机实测 `172.16.48.122:8000`） |
| HTTP-FLV 兜底 | 带正确 key→HTTP 200；无/错 key→403 |

L0 单测覆盖与构建方式：`test/Makefile` 在 Linux 上通过 `NGX_SRC` 自动定位一棵已 configure 的 nginx 树（默认扫 `../nginx-rtc-example/build/src/openresty-*/build/nginx-*` 下带 `objs/ngx_auto_config.h` 的目录），生产源按 nginx 自己的 `-W -Wall -Wpointer-arith` 编译，`-Iinclude` 排在最后、只用于 srtp2 等 nginx 不带出的头。`test/nginx_stub.c` 仍随主套件编译，但在真实头文件模式下只补 nginx 运行时符号，不再冒充 `ngx_slab_pool_t`/`ngx_event_s` 等结构布局；纯 stub 世界（`include/`）保留给 Windows 交叉构建。`cd nginx-rtc-module/test && make test` 输出 `TOTAL: 145 PASS: 145 FAIL: 0`。其中 `rtp_b_frame_b_and_b1_slices`/`rtp_b_frame_non_b_slices`/`rtp_b_frame_nonzero_first_mb` 曾作为 B 帧识别的回归断言（早期 `read_ue` 用按位或累加后缀导致 `slice_type 6/2` 误判），修复后转绿。

两个驱动脚本都以 `make -C test` 变量覆盖驱动，`test/Makefile` 不含 sanitizer 知识，普通 `make -C test test` 照常可用：

| 脚本 | 作用 | 产物 |
| --- | --- | --- |
| `nginx-rtc-module/scripts/sanitize-tests.sh` | `SAN=address,undefined`（默认）/`address`/`undefined`/`thread` 下分组建二进制跑，主套件、srtp、dtls、audio、audio_worker 各自链接；需 `build/third`（或 `NGX_RTC_THIRD`）下的 `libsrtp2.a`，否则 srtp/audio 组跳过 | `test/build-asan/<san>/run_tests_<group>` |
| `nginx-rtc-module/scripts/cross-win64-tests.sh` | MinGW 交叉编译纯 C 协议核心（`MINGW_PREFIX` 默认 `~/.local/mingw`），不涉及 nginx 与三方库 | `dist/win64/run_tests.exe` + `libcrypto-3-x64.dll`、`libwinpthread-1.dll`；有 `zip` 时另出 `dist/nginx-rtc-win64-tests.zip` |

说明：srtp/audio/dtls/audio_worker 单测不在默认主套件里，需经 `sanitize-tests.sh` 的对应分组运行。`sanitize-tests.sh` 用 `EXTRA_CPPFLAGS` 追加第三方 include（不覆盖 `CPPFLAGS`，以免丢掉真实 nginx 头文件路径与 `-D_GNU_SOURCE`）；`cross-win64-tests.sh` 则刻意直接覆盖 `CPPFLAGS`，把构建切到 stub 世界——真实 nginx 头文件是 Linux configure 的产物，不能用于交叉目标。

### 2.3 推流命令（测试信号源）

权威入口是 `./run.sh push`（自动生成 HMAC token 并推 `live/livestream`）。等价的裸 ffmpeg 命令如下——URL 鉴权走 HMAC `t`/`sign`，线上不传明文 key：

```bash
export PUSH_KEY=demo-secret-0123456789abcdef0123456789abcdef   # 与 stream_keys.lua 的 live/livestream 一致
EXP=$(( $(date +%s) + 3600 ))
SIGN=$(printf '%s' "live/livestream|t=${EXP}" \
       | openssl dgst -sha256 -hmac "$PUSH_KEY" -binary | base64 | tr '+/' '-_' | tr -d '=')

ffmpeg -re -f lavfi -i testsrc2=size=640x360:rate=30 \
    -f lavfi -i sine=frequency=1000:sample_rate=48000 \
    -c:v libx264 -preset ultrafast -tune zerolatency -g 30 -bf 0 -pix_fmt yuv420p \
    -maxrate 2500k -bufsize 1000k \
    -c:a aac -b:a 64k -ar 48000 \
    -f flv "rtmp://127.0.0.1:1935/live/livestream?t=${EXP}&sign=${SIGN}"
```

参数说明：`-bf 0` 禁止 B 帧（与服务端 B 帧过滤双保险）；`-g 30` 每 1 s 一个 IDR（640x360@30fps，`run.sh push` 与转码档一致）；`-tune zerolatency` 压低编码端缓冲；`-maxrate/-bufsize` 压住 ultrafast I 帧突发（`run.sh push` 注释实测不压时原流约 52% 丢包）；`t`（过期 unix 秒）与 `sign=base64url(HMAC-SHA256(secret, "live/livestream|t=<t>"))` 供 RTMP `on_publish` 推流鉴权（`run.sh push` 自动带，`PUSH_KEY` 默认 `demo-secret-0123456789abcdef0123456789abcdef`）。ffmpeg 打印 `frame=...  fps=...  q=...` 即推流正常。也可改用真实编码器/OBS 推 `rtmp://127.0.0.1:1935/live/livestream?t=<exp>&sign=<sign>`。

## 3 端到端测试与判定

### 3.1 执行步骤

```bash
cd /home/dgliu/workspace/webrtc
./run.sh stop      # 幂等清理旧 nginx / ffmpeg
# 终端 A：推流
./run.sh start     # = ./run.sh nginx + ./run.sh push（前台 ffmpeg）
# 终端 B：验证
./run.sh verify    # = node client/play.mjs
```

也可分步：终端 A `./run.sh nginx` 后 `./run.sh push`，终端 B 随时 `./run.sh verify`。`run.sh nginx`/`start` 内部先自动探测主网卡 IP 生成 `conf/nginx.rtc.conf`（`RTC_CANDIDATE_IP` 可覆盖）；`run.sh push` 推流 URL 自动签 `?t=<exp>&sign=<HMAC>`（secret 取 `PUSH_KEY`，默认 `demo-secret-0123456789abcdef0123456789abcdef`）。

### 3.2 预期输出与判定

`play.mjs`（werift，`useH264/useOPUS`、recvonly 双 transceiver）典型输出：

```
[track] audio audio/opus
[track] video video/H264
[play] code: 0
[sdp] answer set, waiting for DTLS/SRTP media...
[keyframe] first H264 IDR at xxx ms

=== RTMP -> WebRTC media receive result ===
audio: packets=389 bytes=6xxxx codec=audio/opus first_packet_ms=5xx loss_rate=0% jitter_ms=x bitrate_kbps=xx
video: packets=761 bytes=3xxxxx codec=video/H264 first_packet_ms=5xx loss_rate=0% jitter_ms=x bitrate_kbps=xxx fps=xx keyframes=xx
video: first_keyframe_ms=xxx (首个 H264 IDR 到达, 真正出图延迟口径)

[PASS] 音视频均经 WebRTC 收到 RTP 包
```

判定标准（硬性）：打印 `[PASS]`，即 `stats.audio.pkts>0 && stats.video.pkts>0`，进程退出码 0。若为 `[FAIL]`，按 3.3 顺序排查。`first_packet_ms` 为各自首包到达延迟，`first_keyframe_ms` 为首个可解码 H264 IDR 到达延迟（真实出图口径，与「首包」不同）。`loss_rate`/`jitter_ms`/`bitrate_kbps`/`fps`/`keyframes` 为播放端从 RTP 头计算，可作质量旁证。

**丢包率的口径**：`loss_rate_percent` 只统计每条 track **收到首包之后 `--warmup`（默认 1000 ms）以外**的窗口。SRTP 就绪后服务端立即回放 fast-start GOP，首包起的那一簇序列不连续是刻意的，逐包实测缺口落在第 3 个收到的包上、幅度 8~11826 包；按整窗计算会在一条没丢包的链路上报出 1.4%~83%。被排除的量不隐藏：结果里 `lost_packets`（预热后）+ `warmup_lost_packets`（被排除）恒等于 `lost_packets_all`（整窗），`--warmup 0` 可还原旧的整窗口径。`packets`/`bytes`/`bitrate_kbps`/`fps` 仍是整窗统计，不切窗口。

`--json` 每路输出**一行** JSON（NDJSON）：`--stream` 可重复，每路一行，换 JSON 数组会让既有的单路消费者拿到 list。单路时即"单个 JSON 对象"，与旧版键兼容（只增字段）。

### 3.3 失败定位

| 现象 | 排查点 | 命令/日志 |
| --- | --- | --- |
| `[play] code:` 非 0 | 鉴权或 offer 解析 | 见 §4；`grep "ngx_rtc_http:" logs/error.log` |
| 停在 `waiting for DTLS/SRTP` | UDP 8000 未达 / STUN ufrag 未匹配 | `grep "ngx_rtc_stream: unknown ICE ufrag" logs/error.log`；`ss -lunp \| grep 8000` |
| video 有包 audio 0 包 | 推流无音频或 AAC 序列头未到 | 确认 ffmpeg `-c:a aac` 且已过首帧；转码在首个 ASC 后才建 `audio_ctx` |
| audio 有包 video 0 包 | 推流无视频或非 H264 | 确认 `-c:v libx264`；看 `grep "new session"` 后 source 是否收到 SPS/PPS |
| 全 0 包 | 未在推流 / candidate 不可达 | `./run.sh push` 观察 ffmpeg 帧计数 |

补充日志事实：每个播放会话在 `ngx_rtc_http_module` 打印 `new session stream=live/livestream ufrag=<hex>`（info 级，error.log 需 `error_log logs/error.log info`），用于对拍会话建立。

## 4 鉴权测试与密钥热更新

### 4.1 请求体

鉴权是 **HMAC token**，不是明文 key：`stream_keys.lua` 每个 `app/stream` 存一个 secret（仅服务端持有），客户端用 `t`（过期 unix 秒）与 `sign=base64url(HMAC-SHA256(secret, "<app>/<stream>|t=<t>"))` 自签，请求体不传 secret。信令鉴权在 Lua 层（`access_by_lua_file conf/auth.lua`）先于 RTC 模块执行：IP 限流（`resty.limit.req` 0.5 req/s + burst 5）→ 解析 `streamurl` 的 `app/stream` → `config.verify(appstream, t, sign)`（`conf/hmac.lua` 常量时间比较；过期/伪造一律 403）。判定顺序决定预期码：

| 场景 | 请求特征 | 预期 HTTP 码 | 说明 |
| --- | --- | --- | --- |
| token 正确 | `t` 未过期、`sign` 与 secret 匹配 | 200 | 放行进入 SDP 处理（offer 合法→`code:0`） |
| sign 错误 | `t` 合法、`sign` 不匹配 | 403 | Lua 层拒绝，不触达 SDP |
| t 缺失/过期 | 无 `t` 或 `ngx.time() > t + 60` | 403 | `config.verify` 返回 false；60 s 为时钟倾斜余量 |
| streamurl 非法 | `streamurl` 非 `webrtc://h/a/s` 形态 | 400 | Lua 正则不匹配即 400 |
| 限流超限 | 同一 client IP 持续超 0.5 req/s 或突发超 burst 5 | 429 | `limit_req` rejected，返回 JSON `{"code":429,...}` |

### 4.2 命令示例

```bash
BASE=http://127.0.0.1:18082/rtc/v1/play/
APPSTREAM=live/livestream
SECRET=demo-secret-0123456789abcdef0123456789abcdef   # stream_keys.lua 中 live/livestream 的值

# 签 token: sign = base64url(HMAC-SHA256(secret, "<app/stream>|t=<t>"))
mkbody() {  # <exp> <sign>
  printf '{"streamurl":"webrtc://127.0.0.1:18082/%s","t":"%s","sign":"%s","sdp":"x"}' \
      "$APPSTREAM" "$1" "$2"
}
EXP=$(( $(date +%s) + 3600 ))
SIGN=$(printf '%s' "${APPSTREAM}|t=${EXP}" \
       | openssl dgst -sha256 -hmac "$SECRET" -binary | base64 | tr '+/' '-_' | tr -d '=')

# 1) 错误 sign -> 403（Lua 拒绝，body 无需是合法 SDP）
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' -d "$(mkbody "$EXP" bad)"
# 期望 403

# 2) 正确 sign + 非法 SDP -> 400（证明已过鉴权，失败在 SDP 解析）
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' -d "$(mkbody "$EXP" "$SIGN")"
# 期望 400（而非 403）

# 3) 正确 sign + 合法 offer -> code:0（等价于 ./run.sh verify 的 POST）
#    直接跑 play.mjs 即可：node client/play.mjs（内部按同一规则签 t/sign）

# 4) 限流：0.5 req/s + burst 5，快速连打 40 次，末段期望 429
for i in $(seq 1 40); do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
    -H 'Content-Type: application/json' -d "$(mkbody "$EXP" "$SIGN")"
done | sort | uniq -c
# 期望：前若干次 400（过鉴权、SDP 非法），随后 429
```

### 4.3 密钥热更新（免 reload）

secret 来源：`stream_keys.lua` → `config.lua` 每 10 s `reload()` 写进 `lua_shared_dict stream_keys`（`nginx.conf` 的 `init_worker_by_lua_block` + `ngx.timer.every(10)`）。

| 方法 | 操作 | 生效 |
| --- | --- | --- |
| 改文件热加载 | 编辑 `conf/stream_keys.lua` 增删条目 | ≤10 s 后自动生效，无需 reload |
| 运行期管理 API | `POST /admin/keys`（仅 127.0.0.1）增删 | 立即写入 shared dict；注意下个 10 s reload 会被文件内容覆盖 |

```bash
# 管理 API：列出 / 增 / 删（loopback-only，nginx.conf allow 127.0.0.1）
# 这里的 "key" 字段是新的 HMAC secret，不是明文口令
curl -s http://127.0.0.1:18082/admin/keys                 # {"code":0,"keys":[...]}
curl -s -X POST http://127.0.0.1:18082/admin/keys \
  -H 'Content-Type: application/json' \
  -d '{"action":"add","appstream":"live/ephemeral","key":"tmp-secret-0123456789abcdef0123456789"}'
# 立即用该 secret 签 token 播放应通过鉴权；10 s 后 reload 从文件恢复，临时条目失效

# 改文件热加载示例：["live/hotreload"]="hot-secret-67890abcdef0123456789abcdef0"（已预置）
sleep 11
HOT=$(printf '%s' "live/hotreload|t=${EXP}" \
      | openssl dgst -sha256 -hmac "hot-secret-67890abcdef0123456789abcdef0" -binary \
      | base64 | tr '+/' '-_' | tr -d '=')
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' \
  -d "{\"streamurl\":\"webrtc://127.0.0.1:18082/live/hotreload\",\"t\":\"$EXP\",\"sign\":\"$HOT\",\"sdp\":\"x\"}"
# reload 前 403，reload 后 400（已过鉴权），证明 secret 热生效
```

## 5 兜底播放与 candidate 验证

### 5.1 HTTP-FLV 兜底（保留路径）

前提：正在推 `live/livestream`。HTTP-FLV 取流经 `flv_auth.lua` 鉴权（`?app=&stream=&t=&sign=`，与信令同一 HMAC 规则），验证 HTTP 状态与 FLV 容器头：

```bash
FLV='http://127.0.0.1:18082/live'
SECRET=demo-secret-0123456789abcdef0123456789abcdef
EXP=$(( $(date +%s) + 3600 ))
SIGN=$(printf '%s' "live/livestream|t=${EXP}" \
       | openssl dgst -sha256 -hmac "$SECRET" -binary | base64 | tr '+/' '-_' | tr -d '=')
QS="app=live&stream=livestream&t=${EXP}&sign=${SIGN}"

# 无 token -> 403
curl -s -o /dev/null -w 'no-token=%{http_code}\n' \
  "$FLV?app=live&stream=livestream"
# 期望 no-token=403

# 正确 token -> HTTP 200
curl -s -o /dev/null -w 'http=%{http_code}\n' "$FLV?$QS"
# 期望 http=200

# 文件头：FLV 版本 1 + 音视频 tag 标记（0x05）
curl -s "$FLV?$QS" | head -c 13 | od -A x -t x1z
# 期望 46 4c 56 01 05 00 00 00 09 00 00 00 00  -> "FLV\x01\x05..."
```

播放器侧可选：`ffplay "$FLV?$QS"` 或 ffmpeg 抽帧（`ffmpeg -i <url> -t 2 -f null -`）。兜底与 WebRTC 并行服务，互不干扰。

### 5.2 candidate 配置与 SDP 校验

candidate 由 `/rtc/v1/play/` location 的 `rtc_candidate_ip`/`rtc_candidate_port` 指令控制。`run.sh` 启动时自动探测默认路由网卡 IP 并 sed 生成 `conf/nginx.rtc.conf`（模板 `nginx.conf` 中 `rtc_candidate_ip 172.16.48.122` 仅占位，可用 `RTC_CANDIDATE_IP` 覆盖）。用 werift 生成 offer、抓取 answer 的 candidate 行：

```bash
node --input-type=module <<'EOF'
import { RTCPeerConnection, useH264, useOPUS } from "werift";
import { createHmac } from "node:crypto";
const pc = new RTCPeerConnection({ codecs: { audio: [useOPUS()], video: [useH264()] } });
pc.addTransceiver("audio", { direction: "recvonly" });
pc.addTransceiver("video", { direction: "recvonly" });
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
const secret = "demo-secret-0123456789abcdef0123456789abcdef";
const t = Math.floor(Date.now() / 1000) + 3600;
const sign = createHmac("sha256", secret).update(`live/livestream|t=${t}`).digest("base64url");
const res = await fetch("http://127.0.0.1:18082/rtc/v1/play/", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ sdp: offer.sdp,
    streamurl: "webrtc://127.0.0.1:18082/live/livestream", t: String(t), sign }),
});
const data = await res.json();
console.log("code:", data.code);
console.log((data.sdp || "").split("\r\n").filter((l) => l.startsWith("a=candidate")).join("\n"));
EOF
```

预期输出含：

```
code: 0
a=candidate:1 1 udp 2130706431 172.16.48.122 8000 typ host generation 0
```

### 5.3 局域网可达性验证

| 检查项 | 命令 | 期望 |
| --- | --- | --- |
| UDP 监听 | `ss -lunp \| grep 8000` | nginx 监听 `0.0.0.0:8000`（或宿主 LAN IP） |
| 本机回环经 LAN IP | 同一主机跑 `play.mjs`（其 SDP candidate 即 `172.16.48.122:8000`） | DTLS 后持续收包 |
| 跨主机（另一台 LAN 机器） | 在该机器把 `play.mjs` 的 `API/STREAM` 域名换成 `172.16.48.122:18082` 后运行 | `[PASS]`；需放行宿主防火墙 UDP 8000 与 TCP 18082 |
| 实际收发统计 | 播放端打印 `audio/video packets` | 与 §3.2 基线同量级 |

跨主机失败时，用 `tcpdump -i any udp port 8000 -c 20`（宿主）确认 SRTP 数据报是否到达；若只见 STUN/DTLS 不见媒体，优先检查 candidate 是否被 NAT/防火墙改写。

## 6 端到端驱动脚本与状态可观测

除 `run.sh verify` 外，`scripts/` 下三个 e2e 脚本各自做定点回归（均要求 nginx 已起；未起时会尝试 `run.sh nginx` 并轮询 `/rtc/v1/stats`）：

| 脚本 | 断言 | 备注 |
| --- | --- | --- |
| `scripts/e2e-play-json.sh` | `/rtc/v1/play/` 返回可解析 JSON，且 answer 含 `v=0`、`a=candidate:`、`a=setup:`、`a=ssrc:` | 回归「响应缓冲区按 `ngx_escape_json(NULL,...)` 的额外字节数而非转义后长度计算」导致的答案越界；推 `live/playjson` 以免与其他 guard 抢名 |
| `scripts/e2e-whip-release.sh` | WHIP 发布者退出后流名释放，并可由 RTMP 重新占用 | 回归跨 worker 发布权泄漏；从 `live/{hotreload,luahotload,whiptest}` 中挑空闲名，用 `rtc_ready_timeout`(30 s)+8 s 为界 |
| `scripts/e2e-asan.sh [ASAN_PREFIX]` | 在 ASan 版 nginx 上串跑 RTMP→WebRTC、WHIP publish、WHIP release 三步并收集 sanitizer 报告 | 前置见编译文档 §3.5；启动 sanitized 实例前**先停普通实例**——1935/18082 不带 `reuseport`，第二实例会 `EADDRINUSE`；UDP 8000 带 `reuseport`，若只改它则内核会把信令与媒体哈希到不同实例。trap 在退出时停 ASan 实例并恢复普通实例 |

`/rtc/v1/stats`（`ngx_rtc_http_module.c`）的会话生命周期字段：

- 每个 `streams[].sessions[]` 条目带 `state`（`UNKNOWN`/`NEW`/`ICE_BOUND`/`DTLS_HANDSHAKE`/`SRTP_READY`），且该数组列出该 source 的**全部**会话，不再只是订阅者；顶层 `session_states` 给出各状态计数。卡在 NEW 或握手中途（尚未 subscribe，或 WHIP 发布者根本不 subscribe）的会话因此可见。
- `client/probe_stuck_session.mjs` 是该导出的回归探针：只做 HTTP 信令，再手工向 UDP 8000 发一个合法 STUN binding（NEW→ICE_BOUND）+ 一个 DTLS record（→DTLS_HANDSHAKE）后沉默，最后要求 `/rtc/v1/stats` 里自己的 ufrag 处于 `DTLS_HANDSHAKE`，退出码 0 才算 PASS。
- `deploy/nginx/conf/metrics.lua` 的 `/metrics` 暴露 `rtc_sessions{state=...}` gauge，数据源即 `session_states`；`CLOSED` 不作为标签（会话关闭即离开注册表，恒零序列反而误导），其余五个状态即使为 0 也输出。

```bash
node client/probe_stuck_session.mjs --quiet
curl -s http://127.0.0.1:18082/metrics | grep '^rtc_sessions'
```
