# RTMP 转 WebRTC 低延迟直播方案：测试文档

> 范围：`ngx-rtc-module` 的测试层次、推流环境、端到端（werift）判定、鉴权矩阵、HTTP-FLV 兜底与局域网 candidate 验证。命令在 `/home/dgliu/workspace/webrtc/` 下执行。

**结论**：权威验收口径是「werift 无头播放器端到端收包」——`./run.sh verify` 打印 `[PASS]`（`audio.pkts>0 && video.pkts>0`）且退出码 0。其上叠加信令鉴权、HTTP-FLV 兜底与 candidate 验证；纯 C 协议核心另有 host 单测。系统按 `app/stream` 持有 HMAC secret，客户端以 `t`（过期 unix 秒）+ `sign=base64url(HMAC-SHA256(secret, "<app>/<stream>|t=<t>"))` 自签，请求体不传 secret。

## 1 测试分层

| --- | --- | --- | --- |
| L0 纯 C 单测 | rtp/sdp/stun/rtcp/hsm/session_fsm/core/ring/avsync/jitter/shm/stream_module | host 单测（对真实 nginx 头文件编译，无 nginx 运行时依赖） | `TOTAL: 149 PASS: 149 FAIL: 0` |

```bash
cd /home/dgliu/workspace/webrtc && ./run.sh nginx     # RTMP 1935 / HTTP 18082 / UDP 8000
```

启动日志关注 `logs/error.log`：应无 `ngx_rtc_stream: DTLS init failed` / `SRTP init failed`。权威推流入口是 `./run.sh push`（自动生成 HMAC token 并推 `live/livestream`）；等价裸 ffmpeg 命令：

```bash
export PUSH_KEY=demo-secret-0123456789abcdef0123456789abcdef   # 与 stream_keys.lua 的 live/livestream 一致
EXP=$(( $(date +%s) + 3600 ))
SIGN=$(printf '%s' "live/livestream|t=${EXP}" | openssl dgst -sha256 -hmac "$PUSH_KEY" -binary | base64 | tr '+/' '-_' | tr -d '=')
ffmpeg -re -f lavfi -i testsrc2=size=640x360:rate=30 -f lavfi -i sine=frequency=1000:sample_rate=48000 \
    -c:v libx264 -preset ultrafast -tune zerolatency -g 30 -bf 0 -pix_fmt yuv420p \
    -maxrate 2500k -bufsize 1000k -c:a aac -b:a 64k -ar 48000 \
    -f flv "rtmp://127.0.0.1:1935/live/livestream?t=${EXP}&sign=${SIGN}"
```

`-bf 0` 禁 B 帧、`-g 30` 每 1 s 一个 IDR、`-tune zerolatency` 压编码缓冲、`-maxrate/-bufsize` 压住 ultrafast I 帧突发；`t` 为过期 unix 秒，`sign` 供 RTMP `on_publish` 推流鉴权。ffmpeg 打印 `frame=... fps=... q=...` 即推流正常。

## 3 端到端测试与判定

```bash
./run.sh stop      # 幂等清理旧 nginx / ffmpeg
./run.sh start     # 终端 A：= nginx + push（前台 ffmpeg）
./run.sh verify    # 终端 B：= node client/play.mjs
```

也可分步：`./run.sh nginx` 后 `./run.sh push`，随时 `./run.sh verify`。`nginx`/`start` 先探测主网卡 IP 生成 `conf/nginx.rtc.conf`（`RTC_CANDIDATE_IP` 可覆盖）；`push` 自动给 URL 签 `?t=<exp>&sign=<HMAC>`（secret 取 `PUSH_KEY`）。`client/play.mjs`（`useH264/useOPUS`、recvonly 双 transceiver）典型输出：

```
[play] code: 0
[video] first_keyframe_ms=xxx (首个 H264 IDR 到达, 真正出图延迟口径)
=== RTMP -> WebRTC media receive result ===
audio: packets=389 bytes=6xxxx codec=audio/opus first_packet_ms=5xx loss_rate=0% lost=0 jitter_ms=x bitrate_kbps=xx
video: packets=761 bytes=3xxxxx codec=video/H264 first_packet_ms=5xx loss_rate=0% lost=0 jitter_ms=x bitrate_kbps=xxx fps=xx keyframes=xx
[PASS] 音视频均经 WebRTC 收到 RTP 包
```

判定（硬性）：打印 `[PASS]`，即 `stats.audio.pkts>0 && stats.video.pkts>0`，进程退出码 0；否则打印 `[FAIL] 未收到媒体包`。`first_packet_ms` 为首包到达延迟，`first_keyframe_ms` 为首个可解码 H264 IDR 延迟（真实出图口径）；`loss_rate`/`jitter_ms`/`bitrate_kbps`/`fps`/`keyframes` 由播放端从 RTP 头计算，作质量旁证。丢包口径：`loss_rate_percent` 只统计每条 track 首包之后 `--warmup`（默认 1000 ms）以外的窗口，`lost_packets` + `warmup_lost_packets` 恒等于整窗的 `lost_packets_all`，`--warmup 0` 恢复整窗口径；`packets`/`bytes`/`bitrate_kbps`/`fps` 始终整窗统计，`--json` 每路输出一行 NDJSON，`--stream` 可重复。

失败定位：

| 现象 | 排查点 | 命令/日志 |
| --- | --- | --- |
| `[play] code:` 非 0 | 鉴权或 offer 解析 | 见 §4；`grep "ngx_rtc_http:" logs/error.log` |
| 停在 `waiting for DTLS/SRTP` | UDP 8000 未达 / STUN ufrag 未匹配 | `grep "ngx_rtc_stream: unknown ICE ufrag" logs/error.log`；`ss -lunp \| grep 8000` |
| video 有包 audio 0 包 | 推流无音频或 AAC 序列头未到 | 确认 `-c:a aac` 且已过首帧 |
| audio 有包 video 0 包 | 推流无视频或非 H264 | 确认 `-c:v libx264` |
| 全 0 包 | 未在推流 / candidate 不可达 | 观察 ffmpeg 帧计数 |

会话建立可对拍：`ngx_rtc_http_module` 每个播放会话打印 `new session stream=live/livestream ufrag=<hex>`（info 级，需 `error_log logs/error.log info`）。

## 4 鉴权测试

鉴权是 **HMAC token**，不是明文 secret：`t` 为过期 unix 秒，`sign=base64url(HMAC-SHA256(secret, "<app>/<stream>|t=<t>"))`。**每流两把 secret**，用哪把取决于 token 用途——`<app>/<stream>|play` 用于观看（会内嵌进 `rtcplayer.html`，按公开信息对待），`<app>/<stream>|publish` 用于推流（仅服务端持有）。签名消息两端相同，隔离来自 secret 不同：用 play secret 签出的 token 在 publish 校验下必然 403。这是必须的——拆开之前两边共用一把 secret，而播放页里就有它，于是**每个能打开播放页的人都能顶掉直播流**。

| 入口 | 校验点 | 用哪把 secret |
| --- | --- | --- |
| `/rtc/v1/play/` | `conf/auth.lua`（access 阶段，先于 RTC 模块） | play |
| `/live`（HTTP-FLV） | `conf/flv_auth.lua`（access 阶段） | play |
| RTMP `on_publish` | `conf/rtmp_auth.lua`（notify 回调 `/rtmp/on_publish`） | publish |
| RTMP `on_play` | 同一份 `conf/rtmp_auth.lua`（notify 回调 `/rtmp/on_play`，按 URI 区分用途） | play |
| `/whip/endpoint` | `conf/whip_auth.lua`（access 阶段） | publish |

信令路径的完整链路：IP 限流（`resty.limit.req` 0.5 req/s + burst 5）→ 解析 `streamurl` 的 `app/stream` → `config.verify(appstream, t, sign, "play")`（`conf/hmac.lua` 常量时间比较）。WHIP 把 token 放在 query string（`?app=&stream=&t=&sign=`），因为 C 侧 `rtc_whip` 只解析 SDP body、不认凭据；RTMP 的 token 由推流 URL 的 query 透传成 notify 的表单字段。

| 场景 | 请求特征 | 预期 HTTP 码 | 说明 |
| --- | --- | --- | --- |
| token 正确 | `t` 未过期、`sign` 与该用途的 secret 匹配 | 200 | 放行进入 SDP 处理（offer 合法→`code:0`） |
| sign 错误 | `t` 合法、`sign` 不匹配 | 403 | Lua 层拒绝，不触达 SDP |
| t 缺失/过期 | 无 `t` 或 `ngx.time() > t + 60` | 403 | 60 s 为时钟倾斜余量 |
| streamurl 非法 | 非 `webrtc://h/a/s` 形态 | 400 | Lua 正则不匹配 |
| 限流超限 | 同 IP 持续超 0.5 req/s 或突发超 burst 5 | 429 | 返回 JSON `{"code":429,...}` |
| **用 play secret 推流** | RTMP `on_publish` 或 WHIP 带 play 签名的 token | 403 | 用途隔离的核心断言 |
| **用 publish secret 观看** | `/rtc/v1/play/` 带 publish 签名的 token | 403 | 反向同样成立 |
| **WHIP 不带 token** | `POST /whip/endpoint?app=&stream=` 无 `t`/`sign` | 403 | 2026-09-11 前为 201（完全无鉴权） |
| **RTMP 播放不带 token** | `ffmpeg -i rtmp://.../live/livestream?t=1&sign=bad` | 拒绝 | 日志 `rtmp_auth: deny play`；2026-09-11 前 RTMP 播放无鉴权 |

三条断言的实际返回值（`live/test` 的两把 secret）：play→play 200、publish→play 403、play→WHIP 403、publish→WHIP 201。

**加 `on_play` 的影响面**（实测）：局域网 WebRTC 测试（`/rtc/v1/play/` + UDP）**不受影响**，梯子 ffmpeg 的 RTMP 拉流本就带 play token 所以照常，**HTTP-FLV 也不受影响**（实测 200 + FLV 头）——`ngx_http_flv_live_module` 不触发 `on_play` notify。受影响的只有不经 HTTP 的裸 RTMP 播放。

```bash
BASE=http://127.0.0.1:18082/rtc/v1/play/; APPSTREAM=live/livestream
SECRET=demo-secret-0123456789abcdef0123456789abcdef   # stream_keys.lua 中 live/livestream 的值
mkbody() { printf '{"streamurl":"webrtc://127.0.0.1:18082/%s","t":"%s","sign":"%s","sdp":"x"}' "$APPSTREAM" "$1" "$2"; }
EXP=$(( $(date +%s) + 3600 )); SIGN=$(printf '%s' "${APPSTREAM}|t=${EXP}" | openssl dgst -sha256 -hmac "$SECRET" -binary | base64 | tr '+/' '-_' | tr -d '=')

curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" -H 'Content-Type: application/json' -d "$(mkbody "$EXP" bad)"        # 403
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" -H 'Content-Type: application/json' -d "$(mkbody "$EXP" "$SIGN")"   # 400（已过鉴权、SDP 非法）
# 正确 sign + 合法 offer -> code:0：直接 node client/play.mjs（内部按同一规则签 t/sign）

# 限流：快速连打 40 次，末段期望 429
for i in $(seq 1 40); do curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" -H 'Content-Type: application/json' -d "$(mkbody "$EXP" "$SIGN")"; done | sort | uniq -c
```

密钥热更新：`stream_keys.lua` → `config.lua` 每 10 s `reload()` 写入 `lua_shared_dict stream_keys`（`nginx.conf` 的 `init_worker_by_lua_block` + `ngx.timer.every(10)`）。改文件 ≤10 s 自动生效，无需 reload；`POST /admin/keys`（仅 127.0.0.1）立即增删，但下个 10 s reload 会被文件内容覆盖。管理 API 的 `"key"` 字段承载新的 HMAC secret（不是 token），且必须带 `"purpose":"play"|"publish"`——省略会被拒，免得把推流密钥写进观看侧。

## 5 兜底播放与 candidate 验证

前提：正在推 `live/livestream`。HTTP-FLV 经 `flv_auth.lua` 鉴权（`?app=&stream=&t=&sign=`，与信令同一 HMAC 规则），验证 HTTP 状态与 FLV 容器头（沿用 §4 的 `SECRET`/`EXP`/`SIGN`）：

```bash
FLV='http://127.0.0.1:18082/live'; QS="app=live&stream=livestream&t=${EXP}&sign=${SIGN}"
curl -s -o /dev/null -w 'no-token=%{http_code}\n' "$FLV?app=live&stream=livestream"   # 403
curl -s -o /dev/null -w 'http=%{http_code}\n' "$FLV?$QS"                              # 200
curl -s "$FLV?$QS" | head -c 13 | od -A x -t x1z
# 期望 46 4c 56 01 05 00 00 00 09 00 00 00 00  -> "FLV\x01\x05..."
```

播放器侧可选 `ffplay "$FLV?$QS"`；兜底与 WebRTC 并行服务，互不干扰。candidate 由 `/rtc/v1/play/` location 的 `rtc_candidate_ip`/`rtc_candidate_port` 控制；`run.sh` 启动时探测默认路由网卡 IP 并 sed 生成 `conf/nginx.rtc.conf`（模板占位值可用 `RTC_CANDIDATE_IP` 覆盖）。用 werift 生成 offer、抓 answer 的 candidate 行：

```bash
node --input-type=module <<'EOF'
import { RTCPeerConnection, useH264, useOPUS } from "werift";
import { createHmac } from "node:crypto";
const pc = new RTCPeerConnection({ codecs: { audio: [useOPUS()], video: [useH264()] } });
pc.addTransceiver("audio", { direction: "recvonly" }); pc.addTransceiver("video", { direction: "recvonly" });
await pc.setLocalDescription(await pc.createOffer());
const secret = "demo-secret-0123456789abcdef0123456789abcdef", t = Math.floor(Date.now()/1000) + 3600;
const sign = createHmac("sha256", secret).update(`live/livestream|t=${t}`).digest("base64url");
const res = await fetch("http://127.0.0.1:18082/rtc/v1/play/", { method: "POST", headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ sdp: pc.localDescription.sdp,
    streamurl: "webrtc://127.0.0.1:18082/live/livestream", t: String(t), sign }) });
const data = await res.json();
console.log("code:", data.code);
console.log((data.sdp || "").split("\r\n").filter((l) => l.startsWith("a=candidate")).join("\n"));
EOF
```

预期输出含 `code: 0` 与 `a=candidate:1 1 udp 2130706431 172.16.48.122 8000 typ host generation 0`。局域网可达性：

| 检查项 | 命令 | 期望 |
| --- | --- | --- |
| UDP 监听 | `ss -lunp \| grep 8000` | nginx 监听 `0.0.0.0:8000`（或宿主 LAN IP） |
| 本机回环经 LAN IP | 同主机跑 `play.mjs` | DTLS 后持续收包 |
| 跨主机 | 另一台 LAN 机器把 `play.mjs` 的 API/STREAM 换成 `<宿主 IP>:18082` | `[PASS]`；需放行 UDP 8000 与 TCP 18082 |
| 跨网段 | `RTC_CANDIDATE_IP=<对该客户端可达的地址> ./run.sh nginx`，客户端 `--api http://<该地址>:18082` | `[PASS]`；前提见下 |
| 实际收发 | 播放端 `audio/video packets` | 与 §3 基线同量级 |

跨主机失败时用 `tcpdump -i any udp port 8000 -c 20` 确认 SRTP 数据报是否到达；只见 STUN/DTLS 不见媒体，优先检查 candidate 是否被 NAT/防火墙改写。

**跨网段的边界**：本栈不是完整 ICE，answer 里只有一条 `a=candidate ... typ host`（取值即 `rtc_candidate_ip`），**没有 srflx、没有 relay**。所以可路由的不同网段能通（前提是该地址从客户端可达、UDP 8000 双向放行——路由/防火墙条件，不是代码开关）；**中间有 NAT 则通不了，且无兜底候选**。多宿主主机（有 `docker0`/`br-*`）上自动探测可能选错网卡，用 `RTC_CANDIDATE_IP` 覆盖，`run.sh` 会打印 `[conf] rtc_candidate_ip=...`。

客户端侧只有两处需要可达：`--api` 的 HTTP 地址、answer 里的 candidate。**`--stream` URL 的 host 从不被访问**（服务端只从中解析 app/stream，token 只签路径），故 `--api http://127.0.0.1:18082 --stream webrtc://172.16.48.122:18082/live/livestream` 这种"控制面走近路、媒体面走 LAN"合法，实测 `[PASS]`。服务端不读请求体里的任何 IP：会话按真实 UDP 源地址认（`sess->peer_addr = c->sockaddr`），鉴权只认 token、不绑 IP；历史上四个客户端都发过的 `clientip` 字段服务端从无一处读取，已删除。

## 6 e2e 驱动脚本与状态可观测

`scripts/` 下的 e2e 脚本均要求 nginx 已起（未起时会尝试 `run.sh nginx` 并轮询 `/rtc/v1/stats`）：

| 脚本 | 断言 / PASS | 退出码 |
| --- | --- | --- |
| `e2e-play-json.sh` | `/rtc/v1/play/` 返回可解析 JSON，answer 含 `v=0`、`a=candidate:`、`a=setup:`、`a=ssrc:`；打印 `PASS: /rtc/v1/play/ JSON framing on live/<stream>` | 0 通过 / 1 失败 / 2 setup 错 |
| `e2e-whip-release.sh` | WHIP 发布者退出后流名释放并可被 RTMP 重新占用；打印 `PASS: WHIP release + cross-protocol takeover on live/<stream> (<s>s)` | 0 通过 / 1 失败 |
| `e2e-audio-survives-player.sh` | 一个观看者断开后发布端音频仍存活；打印 `PASS: publisher audio survived a viewer's teardown (<before> -> <after> packets)` | 0 通过 / 1 失败 / 2 setup 错 |
| `e2e-asan.sh [ASAN_PREFIX]` | 在 ASan 版 nginx 上串跑 RTMP→WebRTC、WHIP publish、WHIP release 三步并收集 sanitizer 报告；末尾 `== e2e steps failed: 0 ==` | 0 通过 / 1 失败 |

`e2e-asan.sh` 前置见编译文档 §5；先停普通实例再启动 sanitized 实例（1935/18082 不带 `reuseport`，否则 `EADDRINUSE`）。`/rtc/v1/stats`（`ngx_rtc_http_module`）的会话生命周期字段：

- `streams[]` 条目含 `name`、`publishing`、`pub_worker`、`cross_worker`、`clients`；`streams[].sessions[]` 列出该 source 的全部会话，各带 `state`（`UNKNOWN`/`NEW`/`ICE_BOUND`/`DTLS_HANDSHAKE`/`SRTP_READY`）；顶层 `session_states` 给出各状态计数。
- `client/probe_stuck_session.mjs` 只做 HTTP 信令，再手工向 UDP 8000 发一个合法 STUN binding（NEW→ICE_BOUND）+ 一个 DTLS record（→DTLS_HANDSHAKE）后沉默，最后要求 `/rtc/v1/stats` 里自己的 ufrag 处于 `DTLS_HANDSHAKE`，退出码 0 才算 PASS。
- `deploy/nginx/conf/metrics.lua` 的 `/metrics` 暴露 `rtc_sessions{state=...}` gauge，数据源即 `session_states`；`CLOSED` 不作标签，其余五个状态即使为 0 也输出。
