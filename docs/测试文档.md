# RTMP 转 WebRTC 低延迟直播方案：测试文档

> 文档范围：`ngx-rtc-module` 的测试方法与判定标准——测试分层、推流环境、端到端（werift）、鉴权、HTTP-FLV 兜底与局域网 candidate 验证。所有命令在本仓库 `/home/dgliu/workspace/webrtc/` 下执行。

**结论**：权威验收口径是「werift 无头播放器端到端收包」：`./run.sh verify` 判定 `audio.pkts>0 && video.pkts>0` 即 PASS，实测值视频 H264 761 包/362 KB、音频 Opus 389 包/67 KB、首包约 560 ms，`play.mjs` 另打印 `video: first_keyframe_ms`（首个 H264 IDR 到达，真正出图延迟口径）。在此基础上叠加三层轻量验证：信令鉴权（正确 key→`code=0`，错误/缺失 key→403，超限→429）、HTTP-FLV 兜底（带 key→HTTP 200 + `FLV` 文件头，无 key→403）、局域网 candidate（answer 含 `a=candidate ... <探测 IP> 8000 ...`）。纯 C 协议核心 host 单测：`ngx-rtc-module/test/` 37 用例全 PASS，并曾以回归断言拦截 B 帧识别缺陷（Exp-Golomb 后缀按位或累加导致 slice_type 6/2 误判），修复后转绿。

## 1 结论与测试分层

| 层 | 对象 | 手段 | 结果 |
| --- | --- | --- | --- |
| L0 纯 C 单测 | rtp/sdp/stun/rtcp/hsm/session_fsm | host 单测（无 nginx 依赖） | `ngx-rtc-module/test/` 37 用例全 PASS |
| L1 端到端收包 | 全链路 | `run.sh` + `play.mjs`（werift） | `run.sh verify` 收包判定 |
| L2 信令与鉴权 | `/rtc/v1/play/` + Lua | curl 注入 key 变体 | 通过（403/429 分支覆盖） |
| L3 兜底与网络 | HTTP-FLV、candidate | curl + `ss` + 抓包 | 通过 |

结果基线（作为预期输出参考）：

| 指标 | 实测值 |
| --- | --- |
| 信令响应 | `{"code":0,...}` |
| 视频 | H264 761 包 / 约 362 KB |
| 音频 | Opus 389 包 / 约 67 KB |
| 首包时延 | 约 560 ms（`first_packet_ms`） |
| 视频首帧 IDR | `first_keyframe_ms`（首个 H264 IDR 到达，出图口径） |
| candidate | 自动探测主网卡 IP + `:8000`（本机实测 `172.16.48.122:8000`） |
| HTTP-FLV 兜底 | 带正确 key→HTTP 200；无/错 key→403 |

L0 单测覆盖与回归：`test/` 37 用例按 rtp 11、stun 6、sdp 5、rtcp 9、hsm 3、session_fsm 3 分布，`make test` 输出 `TOTAL: 37 PASS: 37 FAIL: 0`。其中 `rtp_b_frame_b_and_b1_slices`/`rtp_b_frame_non_b_slices`/`rtp_b_frame_nonzero_first_mb` 曾作为 B 帧识别的回归断言（早期 `read_ue` 用按位或累加后缀导致 `slice_type 6/2` 误判），修复后转绿。

## 2 推流环境与工具准备

### 2.1 前置检查

| 项 | 要求 | 检查命令 |
| --- | --- | --- |
| 服务进程 | nginx 已启动，监听 3 个端口 | `ss -lntup \| grep -E '1935\|18082\|8000'` |
| ffmpeg | 支持 `libx264` + `aac` | `ffmpeg -version` |
| Node.js | 可跑 werift 客户端 | `node --version`；`cd client && npm ls werift` |
| 推流 key | `stream_keys.lua` 含 `live/livestream = demo-key-123` | `grep livestream openresty-rtmp-new/nginx/conf/stream_keys.lua` |

### 2.2 启动 nginx

```bash
cd /home/dgliu/workspace/webrtc
./run.sh nginx                       # 仅启动 nginx（RTMP 1935 / HTTP 18082 / UDP 8000）
```

启动日志关注 `logs/error.log`：应无 `ngx_rtc_stream: DTLS init failed` / `SRTP init failed`。

### 2.3 推流命令（测试信号源）

与 `run.sh push` 完全一致的命令（也可改用真实编码器/OBS 推 `rtmp://127.0.0.1:1935/live/livestream?key=demo-key-123`）：

```bash
ffmpeg -re -f lavfi -i testsrc2=size=640x360:rate=30 \
    -f lavfi -i sine=frequency=1000:sample_rate=48000 \
    -c:v libx264 -preset ultrafast -tune zerolatency -g 60 -bf 0 -pix_fmt yuv420p \
    -c:a aac -b:a 64k -ar 48000 \
    -f flv "rtmp://127.0.0.1:1935/live/livestream?key=demo-key-123"
```

参数说明：`-bf 0` 禁止 B 帧（与服务端 B 帧过滤双保险）；`-g 60` 每 2 s 一个 IDR（640x360@30fps）；`-tune zerolatency` 压低编码端缓冲；URL 末尾 `?key=demo-key-123` 供 RTMP `on_publish` 推流鉴权（`run.sh push` 自动带 `?key=$PUSH_KEY`）。ffmpeg 打印 `frame=...  fps=...  q=...` 即推流正常。

## 3 端到端测试与判定

### 3.1 执行步骤

```bash
cd /home/dgliu/workspace/webrtc
./run.sh stop      # 幂等清理旧 nginx / ffmpeg
# 终端 A：推流
./run.sh start     # = ./run.sh nginx + ./run.sh push（前台 ffmpeg）
# 终端 B：验证
./run.sh verify    # = node client/play.mjs
```

也可分步：终端 A `./run.sh nginx` 后 `./run.sh push`，终端 B 随时 `./run.sh verify`。`run.sh nginx`/`start` 内部先自动探测主网卡 IP 生成 `conf/nginx.rtc.conf`（`RTC_CANDIDATE_IP` 可覆盖）；`run.sh push` 推流 URL 自动带 `?key=$PUSH_KEY`（默认 `demo-key-123`）。

### 3.2 预期输出与判定

`play.mjs`（werift，`useH264/useOPUS`、recvonly 双 transceiver）典型输出：

```
[track] audio audio/opus
[track] video video/H264
[play] code: 0
[sdp] answer set, waiting for DTLS/SRTP media...
[keyframe] first H264 IDR at xxx ms

=== RTMP -> WebRTC media receive result ===
audio: packets=389 bytes=6xxxx codec=audio/opus first_packet_ms=5xx
video: packets=761 bytes=3xxxxx codec=video/H264 first_packet_ms=5xx
video: first_keyframe_ms=xxx (首个 H264 IDR 到达, 真正出图延迟口径)

[PASS] 音视频均经 WebRTC 收到 RTP 包
```

判定标准（硬性）：打印 `[PASS]`，即 `stats.audio.pkts>0 && stats.video.pkts>0`，进程退出码 0。若为 `[FAIL]`，按 3.3 顺序排查。`first_packet_ms` 为各自首包到达延迟，`first_keyframe_ms` 为首个可解码 H264 IDR 到达延迟（真实出图口径，与「首包」不同）。

### 3.3 失败定位

| 现象 | 排查点 | 命令/日志 |
| --- | --- | --- |
| `[play] code:` 非 0 | 鉴权或 offer 解析 | 见 §4；`grep "ngx_rtc_http:" logs/error.log` |
| 停在 `waiting for DTLS/SRTP` | UDP 8000 未达 / STUN ufrag 未匹配 | `grep "ngx_rtc_stream: unknown ICE ufrag" logs/error.log`；`ss -lunp \| grep 8000` |
| video 有包 audio 0 包 | 推流无音频或 AAC 序列头未到 | 确认 ffmpeg `-c:a aac` 且已过首帧；转码在首个 ASC 后才建 `audio_ctx` |
| audio 有包 video 0 包 | 推流无视频或非 H264 | 确认 `-c:v libx264`；看 `grep "new session"` 后 source 是否收到 SPS/PPS |
| 全 0 包 | 未在推流 / candidate 不可达 | `./run.sh push` 观察 ffmpeg 帧计数 |

补充日志事实：每个播放会话在 `ngx_rtc_http_module` 打印 `new session stream=live/livestream ufrag=<hex>`（info 级，error.log 需 `error_log logs/error.log info`），用于对拍会话建立。

## 4 鉴权测试与密钥热更新

### 4.1 请求体

信令鉴权在 Lua 层（`access_by_lua_file conf/auth.lua`）先于 RTC 模块执行：IP 限流（60 s 内 30 次）→ 解析 `streamurl` 的 `app/stream` → `config.check(appstream, key)`。判定顺序决定预期码：

| 场景 | 请求特征 | 预期 HTTP 码 | 说明 |
| --- | --- | --- | --- |
| key 正确 | `streamurl=.../live/livestream`，`key=demo-key-123` | 200 | 放行进入 SDP 处理（offer 合法→`code:0`） |
| key 错误 | 同上，`key=wrong` | 403 | Lua 层拒绝，不触达 SDP |
| key 缺失 | 同上，无 `key` 字段 | 403 | `config.check` 对非 string key 返回 false |
| streamurl 非法 | `streamurl` 非 `webrtc://h/a/s` 形态 | 400 | Lua 正则不匹配即 400 |
| 限流超限 | 同一 client IP 31 次/分钟 | 429 | `rate_limit` 计数 > 30 |

### 4.2 命令示例

```bash
BASE=http://127.0.0.1:18082/rtc/v1/play/
# 1) 错误 key -> 403（Lua 拒绝，body 无需是合法 SDP）
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' \
  -d '{"streamurl":"webrtc://127.0.0.1:18082/live/livestream","key":"bad","sdp":"x"}'
# 期望 403

# 2) 正确 key + 非法 SDP -> 400（证明已过鉴权，失败在 SDP 解析）
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' \
  -d '{"streamurl":"webrtc://127.0.0.1:18082/live/livestream","key":"demo-key-123","sdp":"x"}'
# 期望 400（而非 403）

# 3) 正确 key + 合法 offer -> code:0（等价于 ./run.sh verify 的 POST）
#    直接跑 play.mjs 即可：node client/play.mjs

# 4) 限流：1 分钟窗口内快速打 31 次，末次期望 429
for i in $(seq 1 31); do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
    -H 'Content-Type: application/json' \
    -d '{"streamurl":"webrtc://127.0.0.1:18082/live/livestream","key":"demo-key-123","sdp":"x"}'
done | sort | uniq -c
# 期望：前若干次 400（通过鉴权、SDP 非法），窗口内第 31 次起 429
```

### 4.3 密钥热更新（免 reload）

密钥来源：`stream_keys.lua` → `config.lua` 每 10 s `reload()` 写进 `lua_shared_dict stream_keys`（`nginx.conf` 的 `init_worker_by_lua_block` + `ngx.timer.every(10)`）。

| 方法 | 操作 | 生效 |
| --- | --- | --- |
| 改文件热加载 | 编辑 `conf/stream_keys.lua` 增删条目 | ≤10 s 后自动生效，无需 reload |
| 运行期管理 API | `POST /admin/keys`（仅 127.0.0.1）增删 | 立即写入 shared dict；注意下个 10 s reload 会被文件内容覆盖 |

```bash
# 管理 API：列出 / 增 / 删（loopback-only，nginx.conf allow 127.0.0.1）
curl -s http://127.0.0.1:18082/admin/keys                 # {"code":0,"keys":[...]}
curl -s -X POST http://127.0.0.1:18082/admin/keys \
  -H 'Content-Type: application/json' \
  -d '{"action":"add","appstream":"live/ephemeral","key":"tmp-key"}'
# 立即用 tmp-key 播放应通过鉴权；10 s 后 reload 从文件恢复，tmp-key 失效

# 改文件热加载示例：向 stream_keys.lua 追加 ["live/hotreload"]="hot-key-000"（已预置）
sleep 11 && curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE" \
  -H 'Content-Type: application/json' \
  -d '{"streamurl":"webrtc://127.0.0.1:18082/live/hotreload","key":"hot-key-000","sdp":"x"}'
# reload 前 403，reload 后 400（已过鉴权），证明 key 热生效
```

## 5 兜底播放与 candidate 验证

### 5.1 HTTP-FLV 兜底（保留路径）

前提：正在推 `live/livestream`。HTTP-FLV 取流经 `flv_auth.lua` 鉴权（`?app=&stream=&key=` 参数），验证 HTTP 状态与 FLV 容器头：

```bash
# 无 key / 错 key -> 403
curl -s -o /dev/null -w 'no-key=%{http_code}\n' \
  'http://127.0.0.1:18082/live?app=live&stream=livestream'
# 期望 no-key=403

# 正确 key -> HTTP 200
curl -s -o /dev/null -w 'http=%{http_code}\n' \
  'http://127.0.0.1:18082/live?app=live&stream=livestream&key=demo-key-123'
# 期望 http=200

# 文件头：FLV 版本 1 + 音视频 tag 标记（0x05）
curl -s 'http://127.0.0.1:18082/live?app=live&stream=livestream&key=demo-key-123' | head -c 13 | od -A x -t x1z
# 期望 46 4c 56 01 05 00 00 00 09 00 00 00 00  -> "FLV\x01\x05..."
```

播放器侧可选：`ffplay 'http://127.0.0.1:18082/live?app=live&stream=livestream&key=demo-key-123'` 或 ffmpeg 抽帧（`ffmpeg -i <url> -t 2 -f null -`）。兜底与 WebRTC 并行服务，互不干扰。

### 5.2 candidate 配置与 SDP 校验

candidate 由 `/rtc/v1/play/` location 的 `rtc_candidate_ip`/`rtc_candidate_port` 指令控制。`run.sh` 启动时自动探测默认路由网卡 IP 并 sed 生成 `conf/nginx.rtc.conf`（模板 `nginx.conf` 中 `rtc_candidate_ip 172.16.48.122` 仅占位，可用 `RTC_CANDIDATE_IP` 覆盖）。用 werift 生成 offer、抓取 answer 的 candidate 行：

```bash
node --input-type=module <<'EOF'
import { RTCPeerConnection, useH264, useOPUS } from "werift";
const pc = new RTCPeerConnection({ codecs: { audio: [useOPUS()], video: [useH264()] } });
pc.addTransceiver("audio", { direction: "recvonly" });
pc.addTransceiver("video", { direction: "recvonly" });
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
const res = await fetch("http://127.0.0.1:18082/rtc/v1/play/", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ sdp: offer.sdp,
    streamurl: "webrtc://127.0.0.1:18082/live/livestream", key: "demo-key-123" }),
});
const data = await res.json();
console.log("code:", data.code);
console.log((data.sdp || "").split("\r\n").filter((l) => l.startsWith("a=candidate")).join("\n"));
EOF
```

预期输出含：

```
code: 0
a=candidate:1 1 udp 2130706431 172.16.48.122 8000 typ host generation 0
```

### 5.3 局域网可达性验证

| 检查项 | 命令 | 期望 |
| --- | --- | --- |
| UDP 监听 | `ss -lunp \| grep 8000` | nginx 监听 `0.0.0.0:8000`（或宿主 LAN IP） |
| 本机回环经 LAN IP | 同一主机跑 `play.mjs`（其 SDP candidate 即 `172.16.48.122:8000`） | DTLS 后持续收包 |
| 跨主机（另一台 LAN 机器） | 在该机器把 `play.mjs` 的 `API/STREAM` 域名换成 `172.16.48.122:18082` 后运行 | `[PASS]`；需放行宿主防火墙 UDP 8000 与 TCP 18082 |
| 实际收发统计 | 播放端打印 `audio/video packets` | 与 §3.2 基线同量级 |

跨主机失败时，用 `tcpdump -i any udp port 8000 -c 20`（宿主）确认 SRTP 数据报是否到达；若只见 STUN/DTLS 不见媒体，优先检查 candidate 是否被 NAT/防火墙改写。
